# ADR-006: Align cuprum selection across dependency paths

## Status

Accepted.

## Date

2026-09-25

## Context and problem statement

`lading` reaches `cuprum` by two independent dependency paths, and until this
decision only one of them was constrained.

- **Repository path.** A checkout, a development install, and the test suite
  resolve `cuprum` from `pyproject.toml` through `uv.lock`.
- **Standalone path.** The release workflow runs
  `uv run --script scripts/upload_release_wheels.py`. Task 5.1.3's ADR-005 made
  the uploader a PEP 723 script precisely so it would not import the package,
  and `uv run --script` therefore builds an environment from the script's
  inline metadata and an adjacent lockfile, ignoring the project entirely.

The two paths resolved independently, and they diverged. With cuprum 0.2.0b1
published, a bump to the repository pin alone would have left the release job
-- the one process holding a token with `contents: write` -- running whichever
cuprum PyPI happened to serve for a loose or absent requirement at tag time.
The two paths would also have run different cuprum versions against the same
repository, so a behaviour verified in the test suite need not have been the
behaviour that published a wheel.

The pre-release adds a second hazard. A beta API may change between `b1`, a
later beta, and `0.2.0`, so a published `lading` wheel must not admit an
untested beta through a range.

## Decision Drivers

- The release job is the highest-privilege code in the repository and should
  run the least surprising environment.
- Behaviour verified by the suite should be the behaviour that ships.
- A pre-release API is not a stable interface, and a published wheel should
  name exactly the pre-release that was tested, or none at all.
- The constraint should be enforceable by the deterministic gates, not by
  convention alone.
- Bumping should be a small, explicit, reviewed act rather than an automation
  side effect.

## Decision

Cuprum is selected identically on both dependency paths, and the alignment is
enforced by a contract test.

- **Pin exactly, `cuprum==0.2.0b1`, in both `pyproject.toml` and the
  uploader's PEP 723 block.** No range, and no split with exactness only in
  `uv.lock`. A range would admit an untested beta; a split would leave the
  standalone path loose.
- **Lock each path with its own lockfile.** `uv.lock` covers the repository;
  `scripts/upload_release_wheels.py.lock`, generated by `uv lock --script`,
  covers the standalone path. The script lock deliberately keeps that path's
  own resolution rather than forcing the repository's -- each path is tested
  with its own lock, and only cuprum must agree across them.
- **Align the two paths with a contract test, not a tool.**
  `tests/workflow_contracts/test_cuprum_selection.py` reads both requirement
  sites and both lockfiles and fails when the four disagree, and it checks that
  each lock is fresh with `uv lock --check` and `uv lock --script --check`. A
  gate that a person must remember to run is not an alignment mechanism.
- **Bump cuprum manually.** Dependabot stays configured as it is. A Dependabot
  pull request that bumps cuprum edits only `pyproject.toml` and `uv.lock`, so
  the contract test fails it and auto-merge cannot land it. The red pull
  request is itself the notice that a new release exists. The manual procedure
  is in the developers' guide.
- **Gate the first final release.** No final `lading` 0.x release until cuprum
  0.2.0 final ships and the pin has moved to it, so that no final `lading`
  wheel ever records a pre-release requirement.

## Consequences

- Both paths run the same cuprum, and a divergence fails a gate rather than
  surfacing in a release job.
- A dependency change now touches up to four places that must agree: two
  requirement sites and two lockfiles. That cost is what the contract test
  buys, and the developers' guide gives the procedure.
- Dependabot will not refresh the script lock. An unrefreshed lock stays valid
  and pinned, which is the safe direction; a cuprum bump is manual anyway.
- The pin is temporary. Once 0.2.0 final ships, the procedure moves the pin to
  `0.2.0`, and this ADR's exactness rule still stands. The split held in
  reserve -- a range in `pyproject.toml` with exactness only in `uv.lock` --
  becomes reasonable then and should be reconsidered rather than adopted by
  default.
- The standalone path's `cyclopts` stays at its own resolution (5.0.0) while
  the repository holds 3.24.0. Only cuprum is required to agree, because only
  cuprum's behaviour is what the release job and the suite both depend on.
- This ADR amends [ADR-005](005-release-wheel-publication.md)'s standalone
  script contract. ADR-005 made the uploader a PEP 723 script that does not
  import the package; this ADR adds that the resulting second dependency path
  must be pinned and locked like the first. Nothing in ADR-005 is reversed.
